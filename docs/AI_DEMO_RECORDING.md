# Two-agent demo: recording runbook

This branch adds an experimental two-agent workflow to **Prepare data with AI**. It has been tested end to end in the browser with synthetic data and manual mapping. AI responses were mocked in automated tests; a live OpenAI run must be rehearsed before claiming the agents worked live. The existing practice demonstration in `docs/RECORDING_RUNBOOK.md` remains the fallback.

## 1. Start the app

On Hemnaath's Mac, from a terminal:

```bash
cd ~/Codex-sessions/tripwire-qa/repo
source ../preview-venv/bin/activate
streamlit run app/dashboard.py --server.address 127.0.0.1 --server.port 8502
```

Open http://127.0.0.1:8502. If that port is already in use, use the app already there or start on another port. Select **Prepare data with AI → Two-agent workflow (experimental)**. If it isn't there, check you are running the prototype branch and that your working tree is the version being recorded.

To use the two real OpenAI agents, make `OPENAI_API_KEY` available in the terminal **before starting Streamlit**, or enter it directly in the masked **Use your OpenAI key** field in the app. The field keeps it in the app server's session memory and passes it to OpenAI for requests; it is not a secure credential vault. Only enter it on a trusted host, and do not show it in the video. If you use the environment, restart Streamlit after setting it. `OPENAI_MODEL` optionally selects the model; the default is `gpt-4.1-mini`. Confirm the account has access and make a live test; AI can return different suggestions or errors. Each agent's consent control is separate and sends the displayed metadata to OpenAI. No dataset rows are sent, but metadata and questions can be sensitive.

For another machine, generate synthetic data in a new, empty folder using `from intake_prototype.demo import make_synthetic_inputs` and `make_synthetic_inputs(Path('/path/to/new/demo-folder'))`. Never overwrite an existing directory.

## 3. Rehearse the flow

1. In the chat, enter a demo reviewer role and upload the synthetic table. Inspect the preparation agent's payload and choose **Yes, send it** only if you consent. If using the manual path, say the mappings are manual.
2. Review every proposal. Answer each clarification honestly about the synthetic data, make the decisions, and complete the mapping review. Confirm the data-owner approval and create the prepared copy.
3. Bind the two synthetic folders, confirm the uploaded table is candidate B's clinical table, and save the question above.
4. Inspect the separate question-agent payload and consent before sending it. Review its proposed card and clarifications. Confirm the card only if it matches the question. If using the manual path, select the subtype-mix card yourself.
5. Run the firewall. In the manual browser rehearsal this synthetic run returned **Blocked**, with **1 finding** and the original files unchanged; reruns or code changes can differ, so show the actual result. Open the evidence and show that review is pending.
6. Record a reviewer decision and reason if desired. Choose a reason appropriate to the simulated data. Close the session when finished; choose whether to delete the local findings. Never present these synthetic changes as real patient events.

## 4. Suggested recording (under 3 minutes)

The recording must stay under three minutes: aim to finish by about 2:45, leaving a buffer. Trim narration, not the on-screen evidence, if a take runs long. Narrate only what is on screen, and show the actual agent output.

| Time | On screen | Narration |
| --- | --- | --- |
| 0:00-0:18 | Title screen, then the chat opening | "Research data releases can change silently: same sample count, different data. Driftwire catches that. Today a non-technical data owner prepares a new table just by chatting." |
| 0:18-0:45 | Synthetic upload and preparation-agent consent (show exactly what is sent) | "A data owner brings a new table. Before anything leaves this machine, Driftwire shows exactly what the assistant can see. No rows are sent, only column metadata, and only after consent." |
| 0:45-1:15 | Actual mapping proposals, a clarification, then human approval and the prepared copy | "The assistant proposes field mappings and asks when meaning is unclear. A person approves every change, and the original file is never touched." |
| 1:15-1:40 | Bind releases A and B, enter the question, question-agent consent and its actual card suggestion | "A second assistant maps the research question to one supported check. The researcher confirms the interpretation." |
| 1:40-2:20 | Run the firewall, then open the actual verdict and evidence | "The firewall compares the releases, gives a verdict, and shows the evidence behind it. This is synthetic data, not a patient record." |
| 2:20-2:45 | Human review decision and limitations | "The result stays with a person. Unsupported questions and missing evidence stay visible. This is a research prototype, not a clinical tool." |

Only use narration about agent suggestions if the live agents have actually been run and the output is visible. If no key or AI service is available, use the manual fallback and explicitly say so. Do not represent scripted test output as AI output. If this is also used as a live pitch, keep time for the judges' unseen envelope and questions.
